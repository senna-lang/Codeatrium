# リワーク設計: コードから当時の会話を思い出せるようにする

作成日: 2026-08-07
対象: codeatrium (`loci`)
ステータス: 設計（実装未着手）

---

## 0. 最初に読む要約

### このリワークのゴール【最重要】

> **対応ハーネスが編集したコードには、100% 会話履歴がひも付いている状態にする。**

いまどきコードをまるごと手書きすることはほとんどない。
だから「エージェントが書いたコード」＝「ほぼすべてのコード」であり、
**そこを取りこぼさなければ「どのコードを触っても思い出せる」が実際に成立する**。

このゴールは、次の2つに分解して考える必要がある（達成の保証度が違うため）。

| | 内容 | 保証できるか |
|---|---|---|
| **G1** | 対応ハーネスが編集したファイルは、必ず何かしらの会話が返る | **✓ 仕組みで保証できる**。下回ったらバグ |
| **G2** | そのうち、関数・コンポーネント単位まで特定できる | **△ best-effort**。100%は保証できないが、測って上げる |

G1 が「100%」の本体。**編集記録が1件あれば、ひも付けが必ず1本以上できる**という
不変条件をコードとテストで守る（§8.1）。
G2 が落ちても、検索は U1 から U2 へ自動的に落ちる（§6.2）ので、
**利用者から見れば「聞けば必ず何か返る」状態は保たれる**。

### 何を作りたいか

コードを見ながら「この関数、なんでこう書いたんだっけ」と思ったときに、
**そのコードを書いたときの会話をそのまま引っ張り出せる**ようにしたい。

いま `loci` は「言葉で検索できる会話メモ」を売りにしている。
これを「**コードを手がかりに、当時の判断を思い出す道具**」へ作り変える。

**コマンドの役割を、これに合わせて割り当て直す。新しいコマンドは作らない。**

| コマンド | 役割 | 位置づけ |
|---|---|---|
| **`loci context`** | コードから会話を思い出す | **主機能** |
| `loci search` | 言葉によるセマンティック検索 | 副次機能 |

### 引き方は2通りだけ

| | 何で引くか | コマンド例 |
|---|---|---|
| **U1** | ファイルの中の関数・コンポーネント | `loci context search.py:search_combined` |
| **U2** | ファイルそのもの | `loci context search.py` |

### 今なにが問題か（ひとことで）

コードと会話のひも付けが、**LLMによる要約処理が成功したときにしか作られない**。
そのため要約をスキップした会話・失敗した会話には、ひも付けが1本も残らない。
結果として、いま HEAD にある関数のうち**76%は何を聞いても何も出てこない**。

### 直し方（ひとことで）

ひも付けを作るタイミングを、**LLM要約のあと → 会話を記録する瞬間**に前倒しする。
記録する瞬間なら、ハーネスのログに「どのファイルの何行目を編集したか」が
機械的に正確に残っている。LLMを使わずに済むので、要約の成否と無関係になる。

### 対応ハーネス

Claude Code 専用をやめ、**5つのハーネスに対応する**（codex / opencode / grok / omp-pi）。
ログの形式は5つともバラバラだが、**持っている情報は3種類しかない**（§3.2）。
そこを共通の型に正規化するアダプター層を挟み、core は形式の違いを知らない作りにする。

実測の結果、**5つのうち4つ（claude / codex / opencode / omp-pi）は行番号まで持っていた**。
grok だけが文字列しか持たないので、そこは core が照合して位置を割り出す（§3.3）。

### 用語

このドキュメントで繰り返し出てくる言葉を先に説明する。

| 用語 | 意味 |
|---|---|
| **exchange** | ユーザーの発言1回と、それに対するエージェントの応答をまとめた単位。会話の1往復 |
| **蒸留（distill）** | LLMに exchange を要約させ、要点と文脈を取り出す処理。トークン費用がかかる |
| **palace object** | 蒸留の結果できる要約データ |
| **ひも付け** | 「この会話は、このコードを触った」という関係の記録。DB上のテーブル名は `code_edges` |
| **hunk** | 差分のかたまり。「12行目から5行分を、こう書き換えた」という単位 |

## 1. 今なにが起きているか（実測）

### 1.1 コードから会話を引けていない

```
exchanges（会話の往復）           1774
  うち蒸留済み                    1233
  うち蒸留スキップ                 541
palace_objects（要約データ）      1233
  そのうちシンボルがひも付いたもの     50   ← 1233件中わずか50件 (4.1%)
```

いま HEAD にあるコードを、どれだけ思い出せるかを測った結果:

```
HEAD の関数・クラス: 502個（50ファイル）

関数・クラス単位で、何かしら会話がひも付いている割合: 119/502 = 23.7%
ファイル単位で、何かしら会話がひも付いている割合    :  18/50  = 36.0%
```

つまり**4つに3つの関数は、聞いても何も出てこない**。
「どのコードを触っても思い出せる」には遠い。

### 1.2 根本原因：ひも付けを作る処理が、LLM要約の中にしかない

コードと会話のひも付けは、`save_palace_object`（`distiller.py:236-289`）の中でしか作られない。
この関数はLLM要約が成功した後にしか呼ばれない。

つまり**ひも付けの本数が、LLMを何回実行できたかで決まってしまう**。具体的には:

- 蒸留をスキップした541件は、**仕組み上どうやってもひも付けが0本**
- 1回の実行で20件までという上限（`batch_limit=20`）が、ひも付けの増加速度を縛る
- 蒸留が失敗すると、そのときのひも付けは永久に作られない
- ファイル情報を持っていた蒸留済み130件のうち、シンボルまでたどり着けたのは50件だけ

ひも付けそのものは、LLMを使わなくても作れる情報だ。
それをLLM要約の中に閉じ込めているのが、設計上の間違いだった。

### 1.3 個別の不具合

| # | 場所 | 何が起きているか |
|---|---|---|
| A | `distiller.py:261`<br>`if sym.symbol_name not in body_text: continue` | 「会話の文章の中にシンボル名がそのまま書かれていること」を条件にしている。しかし応答文は平均1087文字の普通の日本語で、`search_combined` のような名前がそのまま出てくることはまずない。だからほとんど弾かれる |
| B | `indexer.py:117`<br>`_extract_text` | 会話を記録するとき、`type == "text"` のブロックだけを保存している。**つまりツール実行の記録（＝実際に書いたコードそのもの）を全部捨てている** |
| C | `rooms` テーブルの `room_type='file'` | LLMに自由記述させているため、実データが `search_py` / `search.py` / `SPEC` / `SPEC.md` / `README` / `readme_documentation` のように揺れている。ファイル名の索引として使えない |
| D | `symbols` テーブル | `id = sha256(名前:ファイル:palace_id)` という作りで、同じシンボルが会話の数だけ行として増える。「シンボルという存在」と「会話とのひも付け」が1つのテーブルに混ざっている |
| E | `search_cmd.py:119-143` | `LIKE '%名前%'` で引いて `LIMIT` するだけ。並び替えがなく、見つからなかったときの代替手段もない |
| F | `resolver.py` の `Symbol` | 終了行（`end_line`）を持っていない。そのため「編集された行が、どの関数の中か」を判定できない |
| G | `_is_external_path` | `site-packages` や `node_modules` は除外するが、**隣のリポジトリを除外しない**。実際に `context-fold` という別プロジェクトのパスが混ざっていた |

## 2. 調査で分かった事実（設計の前提）

ここが設計の土台になる。実際にデータを見て確かめた4つの事実を書く。

### 2.1 各ハーネスのログに、編集した場所が残っている【使う】

Claude Code のログ（`.jsonl`）の `toolUseResult` に `structuredPatch` という項目があった。
Edit でも Write でも入っている。

```json
{"filePath": ".../corpus.py",
 "structuredPatch": [{"oldStart":153, "oldLines":8, "newStart":153, "newLines":12,
                      "lines":["   segment = ...", "-    head = ...", "+    head_uuid = ..."]}]}
```

これで**LLMを使わずに「どのファイルの何行目を編集したか」が正確に分かる**。
`lines` の `+` と `-` の数から、編集の大きさも分かる（あとで並び替えに使う）。
実測では6セッションで117個の差分が入っていた。データ量としては些細。

**同じ情報が、他のハーネスにも別の形で入っている。**
5つのハーネスの実ログを調べた結果（2026-08-07 実機調査）:

| ハーネス | 編集の記録場所 | ファイル名 | 行番号 | 形式 |
|---|---|---|---|---|
| **claude** | `toolUseResult.structuredPatch` | ✓ | **✓ そのまま入っている** | `oldStart` / `newStart` / `lines` |
| **codex** | `payload.patch_apply_end.changes` | ✓ 辞書のキー | **✓ そのまま入っている** | 標準の unified diff（`@@ -3,5 +3,5 @@`） |
| **opencode** | `part.state.metadata.diff` | ✓ `filePath` | **✓ そのまま入っている** | 標準の unified diff（`@@ -1,3 +1,14 @@`） |
| **omp-pi** | `toolCall(edit).arguments.input` | ✓ `[path#hash]` | **✓ そのまま入っている** | 独自形式（`*** Begin Patch` ＋ `SWAP 4.=5:`） |
| **grok** | `tool_call(search_replace/write).rawInput` | ✓ `file_path` | **✗ 無い** | `old_string` / `new_string` だけ |

**5つのうち4つが行番号を持っている。行番号が無いのは grok だけ。**

codex の `changes` は `{ファイルパス: {type, unified_diff | content, move_path}}` という形で、
実測 1280件（`update` 700 / `add` 573 / `delete` 7）。
`add` は全文、`update` は unified diff が入る。
さらに `move_path` があり、**ファイルの移動・改名を追える**（§9 の課題1に効く）。

形式はバラバラだが、**持っている情報は3段階に分かれる**。
この差を吸収するのがアダプター層の仕事になる（§3.2）。

> **調査中の誤りの訂正**：当初 codex はツール呼び出し名（`exec` のみ）を見て
> 「編集記録が無い」と判断したが、これは誤りだった。
> codex は編集を**ツール呼び出しとは別の `event_msg` として記録**しており、
> `payload.patch_apply_end` に構造化された差分が残っている。
> ツール名だけを見ると見落とすので、他ハーネスを追加する際も
> **payload 種別を全部数えてから判断すること。**

> **ステップ1b（実ログ165本相当を実際に読んで検証、2026-08-08）で見つかった訂正2件**：
>
> - **grok**: `old_string`/`new_string` は `rawInput`（`tool_call` イベント側）にしか無いというのは
>   不正確。**完了イベント（`tool_call_update`）側には `content: [{type: "diff", path, oldText, newText}]`
>   という別名のフィールドが存在**し、どちらからでも `TextAnchor` を作れる。
> - **opencode**: `part.state.metadata.diff` の存在は正しいが、**`state.input.filePath` は相対パスのことがある**
>   （例: `./result.py`）。絶対パスは `state.metadata.filepath`（**小文字**、`filePath` ではない）に別途入っている。
>   アダプター実装時にどちらを使うか明示的に決めること。
>
> 詳細な実例は `tests/fixtures/harness_logs/README.md`（合成ログの元にした実ログの読み方の記録）を参照。

これを使えば、不具合A（文章にシンボル名が出てこないと弾かれる問題）を正しく直せる。

**注意：不具合Aの条件を単に削除してはいけない。**
削除すると「そのファイルを1回でも触った会話」が、
そのファイルの全シンボルにひも付いてしまい、精度が崩壊する。
正しい直し方は「**編集された行の範囲と、関数の行範囲が重なっているか**」で判定すること。
そのためには関数の終了行が必要になる（不具合F）。

### 2.2 ログは消える【いちばん重要な制約】

```
DBに記録されている会話:              666件
そのうち元のログがまだ残っているもの:    5件（0.8%）

元ログが残っている exchange:    70件
元ログが消えた exchange:      1704件  ← もう二度と取れない
```

Claude Code はセッションログを一定期間で消している。**残っているのはDBだけ**。

ここから分かること:

1. ひも付けの抽出は、**会話を記録する瞬間にやるしかない**。後からまとめて作り直すことは原理的にできない
2. 過去の1704件について、編集行の情報は**もう永久に手に入らない**
3. だから記録の瞬間には、「今の処理で必要な分」だけでなく**加工前のデータそのものを保存しておく**必要がある。あとで良い抽出方法を思いついても、元ログはもう無いから
4. **実装が遅れるほど、データが恒久的に失われ続ける**

### 2.3 編集の3割はサブエージェントのログに入る【親の会話に戻す必要がある】

```
サブエージェントのログにある exchange: 546件（30.8%）
親セッションのログにある exchange:   1228件
```

STRATA の editor や gsd-executor といったサブエージェントが、実際の編集作業をしている。
だから新しく作るひも付けの約3割は、サブエージェント側の exchange に付く。

ところがサブエージェントの発言内容は「この計画通りに編集せよ」という機械的な指示であって、
**判断の理由はそこには書かれていない**。理由は親セッションにある。

このまま作ると `loci context search.py:search_combined` が
「Editor に142行目の変更が指示された」を返してしまい、
「なぜ hard routing を選んだのか」は返さない。**作りたいものと正反対になる。**

直し方は簡単で、親セッションのIDはファイルパスにすでに入っている:

```
.../projects/-Users-.../<親セッションのUUID>/subagents/agent-xxxx.jsonl
                        ^^^^^^^^^^^^^^^^^^  ここから取れる（確認済み）
```

`conversations` テーブルに親セッションIDの列を足し、
サブエージェントのひも付けが当たったときは**親の会話を優先して返す**。

### 2.4 行番号は時間とともにズレる【目印は「ファイル名＋シンボル名」にする】

編集したときの142行目は、いまの142行目とは限らない。
ファイルが育つにつれてズレていく。

ここを間違えると最悪の壊れ方をする。
行番号をそのまま目印にすると、**確信度100%のまま、全然違う関数を指すようになる**。
「自信満々で間違える」は、この道具にとって一番あってはいけない失敗だ。

そこで**「ファイル名＋シンボル名」を目印にする**。行番号は表示用の付加情報に降格させる。

では、どうやってシンボル名を特定するか。調べた結果:

```
structuredPatch を持つ結果: 118件
  originalFile というキーがある:  118件（100%）
  その中身が空でない:            33件（28%）
```

編集前のファイル内容（`originalFile`）は、キーはあるが中身が空のことが多い（新規作成など）。
これだけでは28%しか賄えない。

**採用する方法：ディスクを読まずに、ログの中身だけで特定する**

当初は「index 実行時にディスク上のファイルを読めばよい」と考えた。
`loci index` は Claude Code の Stop hook で毎ラリー後に動くので、
そのときディスクは編集直後の状態のはずだからだ。

**しかしこれは Claude Code でしか成り立たない。**
他のハーネスは hook が使えない可能性が高い（omp-pi・opencode・grok は
`LOCAL-FIRST-harness-matrix.md` で「fallback レシピが第一級」と結論済み）。
cron や手動で index を回す場合、ディスクはとっくに先へ進んでいる。
**古いディスクを読んで確信度100%を付けるのは、§2.4 冒頭で挙げた最悪の失敗そのもの**になる。

そこで**ログの中身だけで特定する**方針に変える。使える材料は2つ:

1. **`originalFile`**（編集前のファイル全文）に対して `old_start` の位置を解決する
2. **差分の本文**に関数定義の行（`def` / `class` / `function` / `const X = (`）が含まれていれば、そこから読む

実測（Claude のコード系 hunk 72件）:

```
originalFile で特定できる     : 34件
差分本文だけで特定できる       : 36件
どちらかで特定できる（合計）   : 53件 (74%)
どちらでも特定できない        : 19件 (26%)  → ファイル粒度に落とす
```

**26%は関数名を特定できない。これは正直にファイル粒度として扱う**（`granularity='file'`）。
推測で埋めない。

**v1 ではディスク読みを実装しない【決定】**

当初は「index が編集直後に動いたと確実に分かる場合に限って使う」とする案だった。
しかしこの条件は**コード上のどこにも表現されていない**。
アダプターは自分がどう起動されたかを知っているが、core は知らない。
つまり「Stop hook 経路のときだけ」という制約が**文章の中にしか存在しない**状態になる。

**文章だけの制約は、2人目の実装者が必ず破る。**
そして破れたときの症状は「確信度100%で違う関数を指す」という、最悪の壊れ方になる。

したがって **v1 ではディスク読みの経路自体を作らない。**
上の実測どおり、ディスク無しでも74%は特定でき、残りはファイル粒度に落ちるだけで
G1（§0）は守られる。**バグの一種類をまるごと消せる方が価値が高い。**

将来入れる場合は、`indexed_promptly: bool` を port から明示的に渡す形にし、
**制約を型で表現してから**にすること。

既知の誤差：同じターンで同じファイルを複数回編集すると、先の差分の行番号が後の編集でズレる。
差分を順番に処理して累積のズレを補正する。補正しても同じ関数の中に収まることがほとんど。

### 2.5 コミットとの対応付けは弱い【今回は見送る】

```
git commit を実行したツール呼び出し: 3件（6セッション中）
出力にコミットSHAが含まれていたもの: 1件
```

`git blame` で「この行 → このコミット → この会話」とたどる方法を検討したが、
**対応付けの材料が足りない**。ブランチ名と時刻とファイルの重なりから推測するしかなく、
確実な情報にはならない。編集記録と同列に扱うと精度を落とす。

ただし git は、消えてしまうログより長生きする唯一の記録である。
**過去を復元できる可能性が残っている唯一の道**なので、
設計上は将来の拡張として残し、今回は実装しない。

## 3. 設計の中心となる考え方

### 3.1 全体を貫く3つの原則

> **① コードと会話のひも付けは、会話を記録する瞬間に、ログから機械的に作る。LLMは使わない。**
> LLM要約は、すでにあるひも付けに「要点の文章」を後から足すだけの役割にする。

これでひも付けの本数がLLMの実行回数から完全に切り離される。

> **② 記録の瞬間には、加工前のデータをそのまま保存する。今の処理結果だけを保存しない。**

元ログは0.8%しか残らない（§2.2）。
将来もっと良い抽出方法を思いついても、そのときには元データが無い。
だから差分そのものを保存しておく。

> **③ ハーネスごとの形式の違いは、アダプター層で吸収する。core は違いを知らない。**

`LOCAL-FIRST.md` §2.0 で決めた原則（core ⊥ harness ⊥ model）をそのまま守る。
今回はそこに「編集場所の記録」という新しい種類の情報が加わる。

---

### 3.2 ハーネス差の吸収：3種類の「場所の手がかり」に正規化する

§2.1 で見たとおり、5つのハーネスは編集の記録形式がバラバラだった。
しかし**持っている情報は3種類しかない**。そこで、この3種類を共通の型として定義し、
アダプターは「自分が持っているもの」を出すだけにする。

```python
# core/models.py — ハーネス非依存の共通型

@dataclass(frozen=True)
class LineRange:
    """行番号が直接分かる場合"""
    old_start: int | None
    old_lines: int | None
    new_start: int
    new_lines: int

@dataclass(frozen=True)
class TextAnchor:
    """編集前後の文字列だけ分かる場合。core がファイル内容と突き合わせて行を割り出す"""
    old_string: str | None
    new_string: str | None

@dataclass(frozen=True)
class FileOnly:
    """ファイルしか分からない場合"""
    pass

CodeLocator = LineRange | TextAnchor | FileOnly
```

**アダプターは複数の手がかりを同時に出してよい。**
たとえば Claude は `LineRange`（structuredPatch）と `TextAnchor`（oldString/newString）の両方を持つ。
core は精度の高い順（`LineRange` → `TextAnchor` → `FileOnly`）に使う。

#### なぜ `TextAnchor` を core に置くのか

一見すると `TextAnchor` は grok 専用の救済策に見えるが、そうではない。

- **Claude** の Edit 結果にも `oldString` / `newString` が入っている。
  `structuredPatch` が欠けたときの代替経路になる
- **opencode** の編集ツールも `oldString` / `newString` を持つ
- **新規ファイル作成**（Write）では差分に意味がないので、内容から位置を割り出す必要がある

つまり**文字列から行を割り出す処理は、ハーネス共通の core ロジック**である。
アダプターごとに実装させてはいけない。

### 3.3 ハーネスの対応段階：できないことは正直に書く

調査の結果、ハーネスは**編集場所の記録能力で3段階に分かれる**。
これを `EditCapability` として宣言させ、できないことをごまかさない。

| 段階 | ハーネス | 出せる手がかり | U1（関数で引く） | U2（ファイルで引く） |
|---|---|---|---|---|
| **full** | claude / codex / opencode | `LineRange` | ✓ 使える | ✓ 使える |
| **anchor** | grok / **omp-pi（v1では）** | `TextAnchor` | △ 条件付きで使える | ✓ 使える |
| **file_only** | （現時点で該当なし。将来のハーネス用に定義だけ残す） | `FileOnly` | ✗ | △ |

#### omp-pi は v1 では `anchor` として扱う【重要】

§2.1 の表では omp-pi を「行番号あり」に分類したが、**v1 の実装では `anchor` とする。**

理由: omp の patch 形式は**公開仕様のない独自DSL**で、実測すると命令が6種類ある。

```
SWAP 649 / DEL 50 / PUT 13 / REM 4 / MV 2 / CUT 1
例: SWAP 31.=34:   ← 意味を推測はできるが、確証がない
```

`31.=34` の解釈を誤ると**行番号が静かにズレる**。
これは §2.4 で「最悪の失敗」と定義したものそのものになる。

**回避策があるので、無理に解読しない。**
patch 本文の `+` 行がそのまま新しいコード本文なので、
**これを `TextAnchor` の `new_string` として使えば、行の計算を一切せずに位置を特定できる。**
grok とまったく同じ経路で処理でき、実装コストもゼロに近い。

`full` への昇格は、omp のソースまたは公式仕様でDSLを確認できてから行う。

> **なぜ `full` と宣言してはいけないか**：§11.2 のとおり `EditCapability` は公開契約になる。
> 「`full` と宣言したら行番号を出す」ことが外部実装への要求になるため、
> **解読できていない形式を `full` と申告するのは契約違反にあたる。**

**結果として、v1 で `LineRange` を使うのは claude / codex / opencode の3つ。**

#### grok をどう扱うか

grok は `old_string` / `new_string` しか持たないため、
core が**ファイル内容と文字列を突き合わせて位置を割り出す**（§5.3）。

実データ278件で検証した結果:

```
search_replace 呼び出し    : 278件
  ファイルが現存           : 139件
  new_string が現在も一致  :  72件 (現存ファイルの52%)
    うち一致が一意          :  71件 (72件中99%)
```

ここから2つ言える。

1. **当たれば、ほぼ確実に一意**（72件中71件）。
   文字列マッチは「当たるか外れるか」がはっきりしていて、
   **外れたときは黙って間違えるのではなく、単に見つからない**。
   古い行番号を使う方式（自信満々で違う関数を指す）より、失敗の仕方が安全
2. **52%という数字は下限**。この検証は「今日の」ファイルに対して行ったもので、
   編集から時間が経ってコードが変わった分だけ外れている。
   実際には記録した瞬間に照合するので、成功率はもっと高くなる

したがって grok は:

- **U2（ファイル単位）は問題なく使える**
- **U1（関数単位）は、文字列が一意に見つかったときだけ**ひも付ける。
  見つからない・複数箇所に一致する場合は**推測せずファイル粒度に落とす**
- 確信度は `LineRange` 由来のものより一段下げる（§6.3 の `GRAN` で調整）

#### `file_only` を定義だけ残す理由

今回調べた5つはすべて何らかの構造化された編集記録を持っていた。
しかし将来対応するハーネスがそうとは限らない。
そのとき**シェルコマンドを解析して推測するのではなく、正直に `file_only` と宣言させる**ための枠として残す。

**間違ったひも付けは、ひも付けが無いことより悪い。**
この道具は「思い出す」ためのものなので、間違ったものを自信をもって出すのが最悪の失敗になる。

### 3.4 port の定義

`LOCAL-FIRST.md` §5.1 の `HarnessAdapter` に、`LogSource` の一部として次を足す。

```python
class LogSource(Protocol):
    # ... 既存（list_sessions / parse_exchanges / fetch_verbatim / ...）

    def edit_capability(self) -> EditCapability:
        """このハーネスが出せる手がかりの段階を宣言する"""

    def extract_code_touches(self, raw_entries) -> list[CodeTouch]:
        """ログから編集記録を取り出す。CodeLocator に正規化して返す。
        行の割り出し・シンボル特定は core が行うので、ここではやらない。"""
```

**アダプターがやること・やらないこと**を明確にする。

| アダプターがやる | core がやる |
|---|---|
| ハーネス固有の形式を読む（`structuredPatch` / `SWAP n.=m:` / unified diff / `old_string`） | `TextAnchor` から行を割り出す |
| ファイルパスの取り出しと絶対パス化 | プロジェクト内かどうかの判定 |
| `CodeLocator` のどれかに詰める | 行の範囲と関数の範囲の重なり判定 |
| 親セッションの参照を返す（§4.2） | シンボルの特定とひも付けの作成 |
| | 確信度の計算と並び替え |

**禁止事項**（`LOCAL-FIRST.md` §2.0.5 の延長）:

- `core/` が `structuredPatch` や `SWAP` といったハーネス固有の名前を知る
- アダプターが tree-sitter を呼ぶ（シンボル解析は core の仕事）
- アダプターが確信度を決める

## 5. 抽出処理の設計

CLAUDE.md の方針（ドメインロジックは純関数に切り出し、TDDで実装する）に従い、
DBやファイルシステムに触らない純関数として作り、先にテストを書く。

### 5.1 共通の型（core 側）

```python
@dataclass(frozen=True)
class CodeTouch:
    """ハーネス非依存の編集記録。アダプターがこの形にして core へ渡す"""
    harness: str            # 'claude' | 'omp-pi' | 'opencode' | 'grok' | 'codex'
    tool_call_id: str       # 再実行時の重複防止に使う
    file_path: str          # 絶対パス（プロジェクト判定は core が行う）
    touch_kind: str         # 'edit' | 'write' | 'read'
    locators: tuple[CodeLocator, ...]   # §3.2。複数出してよい。精度の高い順に core が使う
    added: int
    removed: int
    ts: str | None
    # 以下は core が後から埋める
    symbol_name: str | None = None
    resolved_by: str | None = None
```

### 5.2 アダプター側：ハーネス固有の形式を読む

各アダプターが実装する。**ここにしかハーネス固有の知識を置かない。**

```python
# adapters/harness/claude.py
def extract_code_touches(self, raw_entries) -> list[CodeTouch]:
    """toolUseResult.structuredPatch → LineRange、
    oldString/newString → TextAnchor。両方あれば両方入れる"""

# adapters/harness/omp_pi.py
def _parse_omp_patch(self, text: str) -> list[LineRange]:
    """'*** Begin Patch' / '[path#hash]' / 'SWAP 4.=5:' 形式を読む"""

# adapters/harness/opencode.py
def _parse_unified_diff(self, diff: str) -> list[LineRange]:
    """'@@ -1,3 +1,14 @@' 形式を読む（標準形式なので実装は最も素直）"""

# adapters/harness/grok.py
def extract_code_touches(self, raw_entries) -> list[CodeTouch]:
    """search_replace の old_string/new_string → TextAnchor のみ"""
```

**テストで押さえる異常系**（ハーネスごとに）：差分の項目が無い / 本文が空 /
行番号が欠けている / パスが相対 / 隣のリポジトリのパス / 新規ファイル（旧側が空）/
JSONとして壊れた行 / 独自形式のパースに失敗。

### 5.3 core 側：手がかりを行の範囲に変換する

**ここがハーネス差を吸収する中心。全ハーネス共通で1つだけ実装する。**

```python
def resolve_line_range(
    locators: tuple[CodeLocator, ...],
    original_content: str | None,
) -> tuple[int, int] | None:
    """手がかりを行の範囲に変換する（純関数）

    優先順位: LineRange → TextAnchor → 変換不能なら None
    TextAnchor の場合は original_content の中から old_string を探して行を割り出す。
    見つからない・複数箇所にマッチする場合は None を返す（推測しない）。
    """

def resolve_symbol_name(
    line_range: tuple[int, int] | None,
    patch_body: list[str],
    original_content: str | None,
    lang: str,
) -> tuple[str | None, str | None]:
    """関数名を特定する（純関数）。戻り値は (symbol_name, resolved_by)

    順に試す（§2.4 の実測にもとづく）:
      1. original_content があれば、そこに対して行範囲を解決 → 'original_file'
      2. 差分本文に関数定義の行があれば、そこから読む → 'patch_body'
      3. どちらも駄目なら (None, None) を返し、ファイル粒度に落とす
    ディスクは読まない（§2.4）。
    """

def normalize_repo_path(file_path: str, project_root: str) -> str | None:
    """プロジェクト内なら相対パスを返す。外部ライブラリや隣のリポジトリなら None（不具合G）"""
```

`resolve_line_range` と `resolve_symbol_name` は
**ファイルもDBも触らない純関数**なので、CLAUDE.md の方針どおり TDD で書ける。
5ハーネス分のテストデータを同じ関数に流し込めば、差が吸収できているか一発で分かる。

#### 書き込みトランザクションを短く保つ【並行性】

`code_touches` の書き込みは、**蒸留とは別トランザクションで、短く完結させる。**

現行 `save_palace_object`（`distiller.py:176-301`）は
`BEGIN`〜`COMMIT` の中で tree-sitter 解析と埋め込みまで行っており、
書き込みトランザクションが長い。
そこへ毎ターンの `code_touches` 書き込みが加わり、
さらに複数ハーネスが同じDBに書くようになると、衝突の確率が上がる。

- 記録の書き込みは「解析→まとめて INSERT→即 COMMIT」で閉じる
- シンボル特定（`resolve_symbol_name`）は**トランザクションの外**で済ませる
  （純関数なのでDB接続を必要としない — この設計がそのまま効く）
- WAL と `busy_timeout=10000` は既存のまま利用する

### 5.4 シンボル解析に終了行と言語を追加

```python
@dataclass

    symbol_name: str
    symbol_kind: str
    signature: str
    line: int
    end_line: int      # ★新規：node.end_point[0] + 1
```

Python / TypeScript / Go の3つの解析処理すべてで `end_line` を埋める。

> `resolver.py` が解析できるのは `.py` / `.ts` / `.tsx` / `.go` の4つだけ。
> それ以外の言語では**ファイル単位のひも付けしか作れず、関数単位では引けない**。

> 関数単位ではこの4言語に限られる。
> 解析器が要らないファイル単位のひも付けを土台に据えているのは、このためでもある。

## 6. 検索コマンドの設計

### 6.0 引き方は2つだけ【確定】

実際の使い方は次の2つであり、これ以外を主な入口にしない。

| # | 何で引くか | 例 | どういうとき |
|---|---|---|---|
| **U1** | ファイルの中の関数・コンポーネント | `search.py` の `search_combined`<br>`Button.tsx` の `Button` | この関数を直そうとしている |
| **U2** | ファイルそのもの | `search.py` | このファイルに手を入れる前に全体を把握したい |

ここから決まること:

- **シンボルは必ずファイルとセットで特定する。**
  いまの `loci context --symbol` は名前だけで全体を検索するため、
  別のファイルにある同じ名前（`extract` / `search` / `run` など）とぶつかる。
  U1 は「どのファイルの」まで含むので一意に決まる
- **行番号は主な入口から外す。**
  エージェントが手にしているのは関数名であって行番号ではない。
  行指定は、IDEの選択範囲を U1 に変換するための内部処理に降格する
- §2.4 で決めた目印「ファイル名＋シンボル名」が、**そのまま検索キーになる**。
  別々の理由から同じ結論になったので、設計の筋は通っている

### 6.0b 【実装前に必ず直す】コンポーネントが解析できていない

U1 の「コンポーネント」は、いまのままでは**引けない**。実際に試した結果:

```tsx
export const Button = ({label}: Props) => ...      // ✗ 取れない
export default function Card({title}) ...          // ✓ 取れる
const useCounter = () => ...                       // ✗ 取れない
export const Panel = React.memo(function Panel...) // ✗ 取れない
class Legacy extends React.Component ...           // ✓ 取れる
```

`resolver.py` は `function_declaration` / `class_declaration` / `method_definition` しか見ていない。
**`const X = () => {}` という書き方を全く拾わない。**
これは現代の React / TypeScript で最も多い書き方なので、
このままでは TS・TSX のプロジェクトで U1 がほとんど動かない。

**追加が必要な解析対象**（`_walk_typescript` に追加する）:

| 対象 | 例 |
|---|---|
| `variable_declarator` + `arrow_function` | `const Button = () => {}` |
| `variable_declarator` + `function_expression` | `const f = function () {}` |
| 関数を包む呼び出し | `React.memo(...)` / `forwardRef(...)` |
| 上記が `export_statement` の下にある場合 | `export const Button = ...` |

`symbol_kind` は `function` に統一する。
`component` という種別を新設しない — JSXを返すかどうかで判定するのは壊れやすく、
検索する側も区別を必要としないため（必要になってから作ればよい）。

Python の同じような書き方（`Foo = lambda: ...`）は実際にはほぼ使われないので対象外。

### 6.1 コマンド【確定】

新しいコマンドは作らない。**既存の2つに役割をはっきり割り当てる。**

| コマンド | 役割 | 位置づけ |
|---|---|---|
| **`loci context`** | **コードから会話を思い出す** | **主機能** |
| `loci search` | 言葉によるセマンティック検索 | 副次機能 |

```bash

# U1: ファイルの中の関数・コンポーネント（主な使い方）

# 補助: 行を指定すると、その行を含む関数に変換して U1 として扱う（IDE選択範囲用）

# ===== 副次機能: loci search =====
loci search "RRF で融合する理由" --json
```

`<ファイル>:<引数>` の引数は、**数値なら行番号、それ以外はシンボル名**として解釈する。

#### 既存フラグの扱い

`loci context` にはすでに `--symbol` と `--branch` がある。壊さずに整理する。

| 既存の形 | 扱い |
|---|---|
| `loci context --symbol "Foo.bar"` | **残す**（互換）。ただしファイル指定が無いため<br>別ファイルの同名シンボルとぶつかる（§6.0）。<br>ヘルプに「ファイル指定付きの形を推奨」と書く |
| `loci context --branch "feature/x"` | **残す**。ブランチ単位の振り返りは U1/U2 とは別の用途 |
| `--json` / `--limit` / `--full` | 位置引数の形でもそのまま使える |

**判定順**：位置引数があれば U1/U2 として扱う。無ければ既存フラグの動作にフォールバックする。

### 6.2 見つからなかったときの探し方

「どのコードを触っても思い出せる」を実際に成立させるのは、ここの作り込みになる。

編集の記録だけでは、ログに残っていないコードや昔からあるコードは永久に0件になる。
そこで**少し外れた場所の記憶でも、正直な確信度を付けて返す**。
これがこの道具の売り文句を本当にする部分だ。

**U1（関数・コンポーネントで引いたとき）:**

| 順番 | 条件 | 表示ラベル | 確信度 |
|---|---|---|---|
| 1 | ファイル名とシンボル名が完全に一致するひも付けがある | `symbol` | 1.00 |
| 2 | 同じファイルに何かひも付けがある | `file` | 0.45 |
| 3 | 同じディレクトリに何かひも付けがある | `directory` | 0.25 |
| 4 | シンボル名とシグネチャで言葉の検索をする | `semantic` | 0.10 |

> **v1 で作らない段：`neighbor_symbol`（同ファイル内の呼び出し関係）**
> 当初は「隣の関数を触ったときの議論が、この関数にも効く」ための段を
> 確信度0.60で入れる設計だった。しかし現行 `resolver.py` は
> **定義しか走査しておらず、呼び出し箇所を取る機能が無い**。
> これは検索層の話ではなく**新しい抽出機能の追加**にあたる。
> 同じケースは段2（`file` 0.45）がほぼ拾えるため、**v1 では作らない。**
> 必要性が実測で確認できてから足す。

**U2（ファイルで引いたとき）:**

| 順番 | 条件 | 表示ラベル | 確信度 |
|---|---|---|---|
| 1 | そのファイルにひも付けがある（シンボルごとにまとめて返す） | `file` | 1.00 |
| 2 | 同じディレクトリにひも付けがある | `directory` | 0.30 |
| 3 | ファイルパスやモジュール名で言葉の検索をする | `semantic` | 0.10 |

U2 は「このファイルについて何が決まっているのか」を知りたい場面なので、
**一番良い1件だけを返すのではなく、シンボルごとにまとめて複数返す**。

上の順番でヒットしたら、下は探さない。
どれも0件なら空を返し「記憶なし」とはっきり伝える。
**適当な結果でごまかさない**（CLAUDE.md の方針）。

U1 の2番目「隣の関数」は、「すぐ隣の関数を直したときの議論が、この関数にも効く」ことが
実際に多いための救済策。同じファイル内の呼び出し関係だけを見る
（tree-sitter で取れる範囲に留め、型の解決まではやらない）。

### 6.3 並び替え

不具合E（並び替えが無い）を直す。

```
score = w_kind    * KIND[edge_kind]
      + w_gran    * GRAN[granularity]
      + w_recency * exp(-経過日数 / 60)
      + w_size    * log1p(added) / 5

KIND = {edit: 1.0, write: 0.8, read: 0.3, mention: 0.2}
GRAN = {line: 1.0, file: 0.5}
```

いまは `indexer.py:88` で `Read` を `Edit` や `Write` と同じ扱いにしているが、これを分ける。
「実装時にどう判断したか」の証拠として、**編集は強く、ただ読んだだけは弱い**。

重みの定数は1か所にまとめて定義し、
種別が増えたときに漏れがテストで検出できるようにする（CLAUDE.md の方針）。

### 6.4 `loci prime` の書き換え【必須】

この道具を主に使うのはエージェントであり、

## 8. 成否をどう測るか

ゴールは §0 の G1（編集したファイルは100%）と G2（関数まで特定）。
**1つの数値にまとめない。**
過去データのせいで数字が永久に低く見え、リワークが成功したのか判断できなくなるため。

### 8.1 G1 は「指標」ではなく「不変条件」として守る【最重要】

「編集したファイルは100%」は、あとから測る指標ではなく、
**コードとテストで守る不変条件**にする。測ってから直すのでは遅い。

```python
# core の不変条件（テストで検証する）
#
# 不変条件1: 編集記録1件からは、必ず1本以上のひも付けができる
#   for touch in code_touches:
#       assert len(edges_from(touch)) >= 1
#
# 不変条件2: ひも付けは最低でもファイル粒度を持つ
#   シンボルが特定できなくても granularity='file' で必ず1本張る
#   （symbol_id=NULL を許すのはこのため）
#
# 不変条件3: プロジェクト外のパスだけが例外
#   normalize_repo_path() が None を返したものは、そもそも記録しない
```

**この不変条件が破れる＝バグ**であり、指標の悪化ではない。

つまり `touches_to_edges`（§5.5）は
「シンボルが見つからなければ何も作らない」ではなく、
**「シンボルが見つからなければファイル粒度で作る」**と実装する。
ここを間違えると G1 が静かに崩れる。

#### 検証方法

```
対応ハーネスが編集したファイルのうち、loci context <file> が結果を返す割合
  → 100% でなければならない。1件でも欠けたら原因を特定する
```

CI で回せる形にする（テスト用のログを流し込み、全ファイルについて確認する）。

### 8.2 G1 を実際に壊す要因：ファイルの改名・移動【対応必須】

不変条件を守っても、**ファイルが改名されるとひも付けが迷子になる**。
記録時のパスと、いま問い合わせるパスが違うためだ。

このリポジトリの実測:

```
git 履歴中の改名・移動  : 10件
HEAD のコード系ファイル : 46件
うち改名歴のあるもの    : 10件（22%）

例: src/logo/__init__.py  → src/codeatrium/__init__.py
    src/logo/db.py        → src/codeatrium/db.py
    （パッケージ名の一括変更）
```

**パッケージ名を一度変えただけで、それ以前のひも付けが全部迷子になる。**
G1 を掲げる以上、これは「未解決の課題」ではなく**対応必須項目**になる。

対応方針（安い順に3段）:

| 段 | 方法 | costs | 効果 |
|---|---|---|---|
| 1 | **codex の `move_path`** を記録する（§2.1） | ほぼ無料。すでにログにある | ハーネス経由の改名を追える |
| 2 | **`git log --follow` 相当**を問い合わせ時に引く | git 呼び出し1回 | git 経由の改名を追える。上の実測10件はこれで拾える |
| 3 | 内容ハッシュによる追跡 | 高い | 段1・2で漏れる分。**今回はやらない** |

段1と段2で実測10件すべてを拾えるため、**初版は段1＋段2**とする。

```sql
-- 改名の記録（v9 に追加）
CREATE TABLE file_renames (
    old_path TEXT NOT NULL,
    new_path TEXT NOT NULL,
    source   TEXT NOT NULL,   -- 'harness' | 'git'
    ts       TEXT,
    PRIMARY KEY (old_path, new_path)
);
```

問い合わせ時に、`file_renames` を逆向きにたどって旧パスでも検索する。

### 8.3 G2（関数まで特定できた割合）をどう上げるか

G1 と違い、こちらは100%を保証できない。上げるための解決手段を、精度の高い順に並べる。

| 順 | 方法 | 使える条件 | 実測 |
|---|---|---|---|
| 1 | 差分本文に関数定義の行が含まれる | いつでも | Claude で50% |
| 2 | `originalFile` / `add` の全文から解決 | 全文がログにある場合 | Claude で47%（1と合わせて74%） |
| 3 | 差分の文脈行を、いまのファイルに文字列照合して位置を出す | ファイルが現存 | grok 実測で52%（下限） |
| — | どれも駄目 | | ファイル粒度に落とす（G1 は守られる） |

**順3を全ハーネス共通で使えるようにするのが、G2 を上げる一番効く手**になる。
grok・omp-pi 用に作る文字列照合（§5.3 `resolve_line_range`）を、
`LineRange` を持つハーネスでも「シンボルが特定できなかったとき」に使い回す設計にしておく。

ディスク読みは §2.4 のとおり **v1 では作らない**。

### 指標1【主指標】思い出せた実感があるか

> 直近Nセッションで実際に触ったファイルすべてに `loci context` を実行し、
> **どの順番（表の何段目）で見つかったかの分布**を記録する

- 1〜2番目（`symbol` / `file`）で返せた割合が、実質的な想起率
- 3〜4番目（`directory` / `semantic`）に落ちる割合が高いほど、
  体験は「思い出す」ではなく「連想する」に近くなる
- あわせて**返ってきた内容に判断の理由が入っているか**を目視で確認する
  （§2.3 の親セッションへの引き上げが効いているかどうか）。ここが売り文句そのもの

測定方法：次の10セッションで編集された各ファイルについて
`loci context <ファイル>:<シンボル> --json` を実行し、`match` ラベルの分布を集計する。

> **なぜこれを主指標にするか**：次の指標2は、機械的に抽出する以上ほぼ自動的に100%になる。
> **抽出処理のテストにはなっても、道具としての良し悪しのテストにはならない。**

### 指標2 これから記録する分の網羅率（抽出処理の健全性チェック）

> リワーク後に記録したセッションで編集されたファイル・シンボルのうち、
> **行まで特定できたひも付け**を持つ割合

- 期待値：仕組み上ほぼ100%
- 100%を下回ったら、抽出のバグか未対応言語。**原因を特定するための内部指標**

### 指標3 過去分の網羅率（上限が物理的に決まっている）

> HEAD にあるシンボル・ファイルのうち、何かしらひも付けを持つ割合

```
今日の時点:
  関数・クラス単位: 119/502 = 23.7%
  ファイル単位   :  18/50  = 36.0%
```

**この数字が信用できるか確認した**：
いまの判定は単なる文字列の部分一致なので、
`search` / `context` / `init` のようなありふれた名前が偶然一致して
数字を水増ししている可能性があった。
実際に調べると、一致した119件のうち6文字以下の短い名前は6件（5%）だけで、
大半は `test_extract_files_dedup` や `_insert_exchange` のような固有性の高い名前だった。
→ **23.7% は水増しされていない。比較の基準として使える。**

（ついでに分かったこと：一致のうち `クラス名.メソッド名` の形式は1件（1%）しかない。
いまの判定はモジュール直下の関数とテスト名に偏っていて、
**メソッドを構造的に取りこぼしている**。）

段階B・Cの移行後にもう一度測る。ログが消えている以上、大きな改善は望めない。
**この数字が伸びなくても失敗ではない**（§2.2 の物理的な制約）。

- `LOCAL-FIRST.md` §5.2 の新式（`hash(harness:source_session_id:source_turn_id)`）への

`exchange_id` を含むため両テーブルの再構築が必要になる。

## 10. 蒸留モデルの選択（local-first）

> このセクションだけ、コード想起の話ではなく**蒸留に使うモデルの話**。
> `LOCAL-FIRST.md` §3.2–3.4 と `LOCAL-FIRST-distill-clients.md` の続きにあたる。

### 10.1 現状：導入時のダウンロードは既に実装済み

調べたところ、この機能の大部分は**すでに動く状態にあった**。

| 要素 | 状態 | 場所 |
|---|---|---|
| FT SLM の自動ダウンロード | **実装済み** | `registry.setup("ollama-ft")` が `ollama pull` を実行 |
| init での検出→提案→選択→設定書き込み | **実装済み** | `cli/__init__.py` の `discover` → `setup` → `recommended_id` → `write_client_config` |
| FT SLM を推奨にする | **実装済み** | `recommended_id()` が `ollama-ft` を優先 |
| 黙って別 vendor に切り替えない | **実装済み** | Ready のみ一覧表示 |

実機確認: `hf.co/sennaLLMLearner/qwen2.5-7b-memory-distiller:Q4_K_M`（4.7GB）は pull 済みで、
`registry.py` の `LOCAL_DISTILL_MODEL` と一致している。

**つまり足りないのは「選択肢の階層」だけ**。以下はその追加分。

### 10.2 追加する概念：3つの階層

| 階層 | 中身 | init での扱い |
|---|---|---|
| **`local`** | FT した蒸留用 SLM（`ollama-ft`） | **推奨・既定**。Ready なら最初に出す |
| **`fast`** | 各プロバイダの高速・非推論モデル（Haiku など） | **次点**。警告なしで選べる |
| **`reasoning`** | 推論モデル（Sonnet / Opus など） | **選べるが注意を1行出す**。ブロックはしない |

### 10.3 なぜ推論モデルを推奨しないか

「local-first だから」だけでは理由として弱いので、技術的な根拠を書いておく。

1. **タスクの性質が合わない** — 蒸留は会話から要点を構造化して抜き出す作業であって、
   多段の推論を必要としない。推論にコストを払っても精度がそれに見合って上がらない
2. **レイテンシが体験に直結する** — 蒸留は SessionStart hook で
   `batch_limit`（既定20）件まとめて走る。1件あたりが遅いとセッション開始が待たされる
3. **件数が多い** — このリポジトリだけで1774件。全件に推論を回すのは費用が釣り合わない
4. **JSON が不安定になりやすい** — 推論モデルは思考ブロックを挟むため、
   構造化出力のパースが崩れやすい。現状 `_validate_palace` ＋1回リトライで吸収しているが、
   失敗率が上がると蒸留の取りこぼしが増える

**ただし品質については正直に書く。** 実測（`HAIKU-VS-LOCAL-DISTILL.md`）:

```
100点満点換算  Haiku 90前後 : Local FT 75〜80前後（差20点弱）
全ての測定で Haiku が優位。逆転は一度も観測されていない
```

**`local` を推奨するのは製品としての方針（無料・ローカル完結）であって、品質判断ではない。**
品質を優先したい人が `fast` を選べるようにしておくのが、この階層を作る理由。

### 10.4 型の追加

```python
# adapters/model/types.py
DistillTier = Literal["local", "fast", "reasoning", "unknown"]

@dataclass(frozen=True)
class ModelClient:
    id: str
    provider: Literal["claude", "openai"]
    model: str
    base_url: str | None
    label: str
    tier: DistillTier = "unknown"   # ★追加
```

既存の `ModelClient` に1フィールド足すだけで済む。既定値があるので後方互換。

### 10.5 階層の決め方

| 対象 | 決め方 |
|---|---|
| registry に登録済みの client（`ollama-ft` / `claude-cli`） | **登録時に宣言する**（確実） |
| ユーザーが `model` を明示指定した場合 | **名前のパターンで best-effort 判定**。判定できなければ `unknown` |

```python
# best-effort のパターン表（core ではなく registry 側に置く）
_TIER_PATTERNS = (
    ("haiku",  "fast"),
    ("mini",   "fast"),
    ("flash",  "fast"),
    ("sonnet", "reasoning"),
    ("opus",   "reasoning"),
)
```

**重要な制約：階層で動作を変えない。表示と注意書きにのみ使う。**

パターン表は必ず陳腐化する（新しいモデル名は予測できない）。
これを機能の分岐に使うと、未知のモデルが動かなくなる。
だから `unknown` でも**そのまま動く**ようにし、階層は「一覧の並び順」と
「注意を出すかどうか」だけに影響させる。

### 10.6 他プロバイダのモデルをハードコードしない

Anthropic 以外の高速モデルも同じ枠で足せるようにするが、
**具体的なモデルIDを設計書やコードに埋め込まない。**

理由: モデルIDは頻繁に変わり、埋め込むと確実に古くなる。
代わりに `openai-compat` client（実装済み）と、registry への登録時に
`tier` を宣言する仕組みで受ける。

```toml
# 例: 任意のプロバイダの高速モデルを使う
[distill]
client = "openai-compat"
model = "<プロバイダの高速モデル>"
base_url = "https://<プロバイダのエンドポイント>/v1"
```

### 10.7 init と実行時の挙動

```text
discover()
  → Ready のものを tier 順（local → fast → reasoning）で一覧表示
  → local が Ready なら recommended として先頭に出す
  → 選択

選択されたものが tier="reasoning" または "unknown" の場合:
  「蒸留は構造化抽出タスクのため、高速な非推論モデルを推奨します」
  という1行を出して、そのまま続行する（ブロックしない）
```

config の書式は既存のまま（`client` / `model` / `base_url`）。
**`tier` は設定ファイルに書かない** — 導出できるものを二重に持つと食い違うため。

### 10.8 このセクションでやらないこと

- 階層による機能制限（`reasoning` を禁止しない。ユーザーの選択を尊重する）
- 他プロバイダのモデルIDのハードコード（§10.6）
- FT モデルの再学習・差し替え（別の作業）
- 現行 `config.toml` の黙った書き換え（`LOCAL-FIRST.md` §7 の non-goal のまま）

> なお、このリポジトリの `.codeatrium/config.toml` は
> まだ旧形式（`provider = "openai"`）のままである。
> `LOCAL-FIRST.md` §3.6 のとおり旧形式は読み続けるので動作に影響はないが、
> `client` 形式への移行は別途行う。

## 11. OSS 公開に向けた設計上の考慮

ローカル実装が完了したら、**新しいリポジトリで OSS として公開する**予定。
ここでは「公開作業の手順」ではなく、**いま設計を決める時点で効いてくる点**だけを書く。

### 11.1 テストデータは合成にする【設計変更】

これまで「生き残っている実ログをテストに使う」前提で書いてきた（§9.1）。
**公開リポジトリではこれができない。**
実ログには会話本文・絶対パス・他プロジェクト名が含まれる。

方針を分ける:

| | 用途 | 置き場所 |
|---|---|---|
| **実ログ** | 各ハーネスの形式を**調べる**ため | ローカルのみ（リポジトリ外） |
| **合成ログ** | **テストに使う** | リポジトリに含める |

合成ログは、5ハーネスそれぞれの最小の形を手で書く。
実ログから「形」だけを写し、中身は無害なダミーに置き換える。

これは公開のための妥協ではなく、**テストとして本来こちらが正しい**:

- 決定的（実ログは内容が変わるし、いずれ消える）
- 小さい
- **異常系を意図的に作れる** — §5.2 で挙げた異常系（差分の項目が無い / 本文が空 /
  行番号が欠けている等）は、実ログに都合よく入っているとは限らない

ただし**形を正確に写すには実ログが要る**ので、ローカルへの退避（§9.1）は引き続き必要。
退避先を**リポジトリ内に置かないこと**。

### 11.2 アダプターの port が公開 API になる【設計変更】

§3.4 で定義した port は、これまで内部の実装詳細だった。
公開後は**第三者がハーネスを追加する入口**になる。

- port の形を安定させる。頻繁に変えると外部の実装が壊れる
- `EditCapability`（§3.3）の宣言は**公開契約**になる。
  「`full` と宣言したなら行番号を出す」ことが外部実装への要求になる
- 「ハーネスの追加方法」を文書化する必要がある

**設計への影響**: §3.4 の表（アダプターがやること／core がやること）は、
そのまま公開ドキュメントに使える粒度で書いてある。**追加の作業は要らない。**

### 11.3 プライバシーを機能として明示する

この道具は**会話ログそのものをDBに保存する**。
個人利用なら自明でも、公開するなら明示的に扱う必要がある。

| 項目 | 現状 | 公開時 |
|---|---|---|
| DBのパーミッション | `0o600`（実装済み） | そのまま。README に明記 |
| 保存するパス | 絶対パス | **相対パスに正規化**（§4.1 で設計済み）。<br>結果としてユーザー名が残らない利点もある |
| `.gitignore` | `.codeatrium/` を除外 | **`loci init` が生成するテンプレートに含める** |
| 外部への送信 | 蒸留時にLLMへ送る | **どの client に何が送られるか**を明記 |

§10 で `local`（FT SLM）を既定の推奨にした設計は、プライバシー面でも筋が通る。
**会話ログを外部APIに送らずに済むのが既定**、と説明できる。

### 11.4 FT モデルを既定の推奨にし続けるか【要判断】

`ollama-ft` を推奨既定にしているが、公開すると意味が変わる。

- 第三者が個人アカウント（`sennaLLMLearner`）から 4.7GB を落とすことになる
- モデルの品質・可用性・ライセンスに対する責任が発生する
- 実測品質は Haiku 90 : Local FT 75〜80（§10.3）

判断が要る点:

1. モデルカードとライセンスを用意するか
2. モデルが落とせないときの挙動 — **現状の実装で妥当**
   （`setupable` のまま Ready にしないので、一覧に出ず壊れない）
3. 推奨を維持するか、「local-first を選ぶなら」という条件付きにするか

**設計としては現状のままでよい。** 公開前にモデルカードとライセンスを用意すれば足りる。

### 11.5 公開時の説明は G1 と G2 を分ける

§0 のゴール「編集したコードは100%」は、**README に書くと誇張になりやすい**。

| | 書いてよいか |
|---|---|
| 「対応ハーネスが編集したファイルは、必ず何か返る」（G1） | **✓ 保証できる** |
| 「どのコードでも関数単位で当時の判断が出る」（G2） | **✗ 保証できない** |

対応言語の限定（§5.4）も明記する。
**ファイル単位は言語非依存、関数単位は Python / TypeScript / Go の4拡張子のみ。**

理由は工数ではなく、**git では移動できないデータがここに紐付いているため**。

1. `.codeatrium/memory.db`（1774 exchanges）は git 管理外。
   ベースライン 23.7% も G1/G2 の測定も、このDBが前提
2. 生き残っている `.jsonl` 5本は**このプロジェクトパスに紐付いている**

> ⚠️ **作業ディレクトリを移動・改名した時点で、Claude Code は別プロジェクトとして扱う。**
> セッションディレクトリはパスから機械的に決まるため
> （`/Users/senna/Documents/Repos/logosyncs` → `-Users-senna-Documents-Repos-logosyncs`）、

#### 乗り換えは出荷点の直後（ステップ6 → 7 の間）

| 時点 | 状態 |
|---|---|
| ステップ6完了 | リワークが実データで動くと測定済み／合成フィクスチャが存在する（マシン非依存） |
| ステップ7以降 | 移行・他ハーネス・後始末。**新リポジトリでやる方が良い**（外部コントリビュータが入るのはここから） |

先に未コミットの作業（local-first / adapters、13ファイル）を landする。移行を挟むと差分が絡む。

### 11.8 改名が触るもの【乗り換え時にまとめて実施】

新OSS名を決めると、コード上の3か所が連動する。**ステップ1〜6の間はやらない**（差分が濁るため）。

| 対象 | 現状 | 影響 |
|---|---|---|
| データディレクトリ名 | `paths.py:10` `CODEATRIUM_DIR = ".codeatrium"` | **既存の自分のDBが見つからなくなる**。移行導線が要る |
| CLI 名 | `pyproject.toml:54` `loci = "codeatrium.cli:app"` | `loci` を変えるなら entry point も変わる |
| フック登録 | `hooks.py` が `~/.claude/settings.json` に絶対パスで登録 | **改名すると既存フックが壊れる**。再インストール導線が要る |

推奨: データディレクトリの解決を「新名 → 見つからなければ `.codeatrium/`」の
フォールバック付きにし、一度だけ移行を提案する。利用者はほぼ自分だけなので、これで足りる。

> **改名前に直しておくべき既存の不整合**
> `paths.py` に `CODEATRIUM_DIR = ".codeatrium"` があるのに、
> `config.py:49` は `project_root / ".codeatrium" / CONFIG_FILENAME` と
> **文字列を直書きしている**。
> このまま改名すると片方だけ直して壊す典型パターンになる。
> CLAUDE.md の「単一の正規な情報源」に反しているので、**改名の前に定数へ寄せる。**

- 新しいリポジトリ名・パッケージ名そのものの決定（製品判断）
- 公開時期とリリース手順
- `docs/internal/` のどれを公開するかの選別
- 既存 `Codeatrium` リポジトリの扱い（アーカイブするか、後継を案内するか）

## 12. まとめ

0. **引き方は「ファイル内の関数・コンポーネント」と「ファイル」の2つだけ**（§6.0）
1. **ひも付けを作るタイミングを、LLM要約のあとから、会話を記録する瞬間へ前倒しする** — すべての土台
2. **Claude Code のログにある編集行の情報を使う** — 文章にシンボル名が出てこないと弾く判定を、行の重なり判定に置き換える
3. **目印は「ファイル名＋シンボル名」。これがそのまま検索キーになる** — 行番号は時間とともにズレる
4. **加工前のデータを保存する** — ログは0.8%しか残らない
5. **シンボルの情報とひも付けを別テーブルに分ける** — 定義元を1か所にする
6. **サブエージェントのひも付けは親の会話に引き上げる** — 判断の理由は親側にある（3割が該当）
7. **見つからなかったときの段階的な探し方で「どのコードでも」を成立させる** — 確信度を正直に表示する
8. **`loci prime` を書き換える** — ここをやらないとエージェントの動きは変わらない
9. **主指標は「思い出せた実感があるか」** — 網羅率は抽出処理のテストにしかならない
10. **ハーネス差は「3種類の場所の手がかり」に正規化して吸収する**（§3.2） — core は形式を知らない
11. **できないハーネスは、できないと宣言する**（§3.3） — codex は U1 非対応。間違ったひも付けより正直な空の方がよい
